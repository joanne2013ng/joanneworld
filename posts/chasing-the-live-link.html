Chasing a 404: How I Found My Blog Was Already Live on Vercel

August 4, 2026

Right after publishing my last post about a Claude Code / GitHub hiccup, I wanted to see it live on my actual site. That turned into its own small saga — not because anything was broken, but because I went looking for the fix in the wrong place entirely.

The problem: a 404 where a post should be

I opened what I assumed was my site's URL and got GitHub's own 404 page, not a blog post. My first guess was the obvious one: GitHub Pages must not be turned on for the repo yet. Reasonable guess — this is a plain static HTML site, and GitHub Pages is the default way to serve one straight from a repo.

Down the GitHub Pages rabbit hole

So I went to enable it, and ran into one snag after another, all on mobile web:

  • The Settings tab wasn't visible in the repo's top navigation at all — it turned out to be hidden inside a collapsed More menu.
  • Once inside, GitHub showed "You don't have access to repository options" — which looked like a permissions problem, but was actually just how the mobile view renders before you've switched to the desktop layout.
  • After requesting the desktop site, the full settings sidebar finally appeared — but a mistap on the sidebar landed on GitHub's "Start a GitHub Enterprise trial" upsell page instead of Pages.

Every one of these was a real obstacle, but none of them were the actual problem. I was troubleshooting a feature (GitHub Pages) that this project had never used in the first place.

The actual fix: check what's already there

The clue was sitting in plain view the whole time — the repo's own "About" section on GitHub, right under the repo name, linked to joanneworld.vercel.app. This site wasn't waiting to be deployed via Pages at all; it was already wired up to Vercel, which auto-builds and redeploys on every push to the production branch.

Checking the Vercel project dashboard confirmed it directly: a "Production Deployment" card showing Status: Ready, built from the exact commit that added the new post, with a live preview thumbnail already showing it at the top of the post list.

No settings to flip, no access to fix — it had deployed itself automatically the moment the commit was pushed. The 404 earlier was just me hitting a URL that was never the right one to begin with.

Takeaway

Before troubleshooting "how do I deploy this," it's worth checking whether it's already deployed somewhere, and how. A repo's About/website link, or its connected dashboard on whatever host is actually wired up, is a faster and more reliable signal than assuming the default (GitHub Pages) is the one in use. In this case the real fix wasn't a setting change at all — it was realizing there was nothing left to do.
