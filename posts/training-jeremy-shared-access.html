Training Jeremy: Giving Him Access to Build on Joanne's World

August 5, 2026

I'm Paul. Jeremy is just getting started with coding, and I wanted to teach him by having him actually push real changes to a real site — this one — instead of a throwaway sandbox. That meant giving him genuine write access, not just showing him a screen recording. Here's the exact procedure I used, step by step, so I can hand it to him (or anyone else I'm onboarding) next time.

1. Add him as a collaborator on GitHub

  1. Open the repo → Settings → Collaborators and teams. On mobile, the GitHub app's own menus don't expose this — open the repo in Safari (or any browser) instead, since the full settings UI only shows up there.
  2. Tap Add people, search for Jeremy's GitHub username, and select his account.
  3. Give him Write access — enough to push commits and open pull requests, not enough to change repo settings or remove collaborators.
  4. Send the invite.

Adding someone doesn't grant access immediately — GitHub sends an email invite, and Jeremy has to accept it before any of his pushes will work.

2. Connect his own Claude Code to the repo

Jeremy has his own Claude Code subscription, so he doesn't need my login at all. Once he accepted the invite, he opened Claude Code on his own phone, started a session, and added joanneworld by name — it showed up automatically because GitHub now recognizes him as a collaborator.

3. Run a real test, not a demo

Instead of just telling Jeremy "it works," I had him make an actual edit and push it, then we watched it travel end to end: his change → a pull request → merged into the repo → picked up by our host → live on the real site. That last hop is where we almost got fooled.

4. The gotcha: not every merge goes live automatically

The site deploys via Vercel, and Vercel only auto-publishes pushes to whichever branch is configured as the Production Branch in its project settings. Our repo doesn't even have a branch called main — everything lives on differently-named branches. The fix was checking Vercel's Settings → Git → Production Branch and confirming it matched the branch we were actually merging into. Once pull requests land on that specific branch, Vercel rebuilds automatically within a minute or two — no extra "publish" step.

5. Merge conflicts are normal, not a sign something's broken

With two people pushing from separate sessions, two pull requests both touched the same nav menu at the same time. That's an ordinary merge conflict, not a failure: it just means git needs a human (or Claude) to decide how to combine both changes rather than picking one and silently dropping the other. Reviewing the conflicting lines and keeping both edits took under a minute.

What I'm teaching Jeremy from this

  • Collaborator access and deployment are two different systems — being able to push to GitHub doesn't automatically mean a change is live, and it's worth knowing where the second wire is before assuming a change "didn't work."
  • A merge conflict is routine, not an emergency — read what both sides changed and combine them.
  • The smallest possible real change (even something invisible, like a code comment) is enough to prove a whole pipeline end to end, without risking anything on the live page.
